# Migrations: rollout, rollback and forward repair

How we change the schema without losing approved records (NRC-25). Conventions for new tables are
in `docs/adr/0001-marketing-service-foundation.md`.

## How migrations run

- `alembic upgrade head` runs as the database owner (`MIGRATION_DATABASE_URL`), as its own release
  step before new API or worker pods start. The login roles `marketing_app` and `marketing_worker`
  must exist first (see "Staging prerequisites" in the README).
- An upgrade run is one transaction (Alembic's default, see `migrations/env.py`), and PostgreSQL DDL
  is transactional. If any revision fails, the whole run rolls back and the database stays on the
  revision it started from. Fix the cause and run it again.
- One exception to plan for: `CREATE INDEX CONCURRENTLY` must run in an `autocommit_block()`, which
  commits everything before it. Keep such a migration to that one index. None exists today.

## What is tested

| Check | Where |
|---|---|
| Empty database to head; models match the schema (`alembic check`); one head | CI, `Migrations apply, match the models and have one head` |
| Foundation schema (`de579cd5c63a`) with real rows, upgraded to head: every existing value unchanged, the API role can still read the rows | `tests/test_migrations.py::test_upgrade_from_the_baseline_keeps_existing_records` |
| Every downgrade to `base`, then upgrade to head again | the session fixture in `tests/conftest.py`, on `marketing_test`, at the start of every test run |
| Forced RLS and tenant-carrying references on every tenant table | `tests/test_isolation.py` |

## Writing a migration

- Make changes additive: add a table, or add a nullable column or one with a server default.
  Backfill, then add the `NOT NULL` or check constraint in a later release.
- Never rename or drop something in the same release that stops using it. First ship code that
  no longer reads it, then drop it in a later migration. To Alembic, a rename looks like a drop
  plus an add, which loses data unless you rewrite it with `op.alter_column(...,
  new_column_name=...)`.
- Edit autogenerated migrations by hand: RLS, grants, composite references, constraint names, and
  `downgrade()`.
- If a migration changes what one role may do (like `3fb9adf5dfbe`), write the deploy order in its
  docstring and in the README.

## Rolling back a release

1. **Roll back the application, not the schema.** Additive migrations keep the previous image
   working on the new schema, so redeploy the previous image tag.
2. **A wrong migration is fixed forward.** Write a new revision that corrects it and deploy that.
   Never run `alembic downgrade` on staging or production.
3. **Lost or damaged data comes back from a backup.** Restore Aurora to a point in time into a new
   cluster (NRC-26), with publishing paused, and compare before switching over. Downgrade and
   upgrade can never bring dropped rows back.

`alembic downgrade` is for local and test databases you can rebuild, and only when nobody else
uses them. On 12 Nov a downgrade on the shared dev database wiped the frontend's seeded tenant.

## What each downgrade destroys

Read from the bottom up: downgrading to a revision runs the `downgrade()` of every revision above
it.

| Revision | Adds | Its downgrade removes | Records lost |
|---|---|---|---|
| `b3e6bfed9303` | Merge of the generation and validation chains | Nothing | None |
| `5b1e0c7d2a91` | `memberships.display_name` | The column | Member display names |
| `172887e987f2` | `validation_runs` | The table | **All validation runs and their evidence** |
| `3fb9adf5dfbe` | `marketing_worker` grants | Grants only | None |
| `56b7fa46620e` | Asset and job lineage keys | Constraints only | None |
| `440a8d5dba9a` | `provider_spend`, job spend columns | Table and columns | Provider spend totals and actual job costs |
| `a3c5e7b91d24` | `assets` | The table | Asset records (the S3 objects stay, unreferenced) |
| `39d93abf9900` | `policy_bundles` | The table | **Approved policy versions** |
| `ffd6ebe6b868` | `jobs`, `outbox_events`, `credit_reservations`, lease function | Tables and function | Jobs, pending events, credit reservations |
| `de579cd5c63a` | Foundation: tenants, members, studies, snapshots, creatives, versions, idempotency | Everything | **Approved study snapshots, every creative and version** |

Revisions in bold hold approved or audit records. Never downgrade past them on a database with
real data.
