# ADR 0001: Marketing service foundation

- Status: accepted, 19 Nov 2026
- Ticket: NRC-25 (epic NRC-29)
- Owner: Dinesh

## Context

Three people build NRC Marketing at the same time: Dinesh (shared schema, API, auth, briefs,
approvals, social publishing), Firoz (policy, GraphRAG, validation, generation, storage, cost) and
Praneeth (frontend). Everyone works against the same database and contract, so we need one record
of who owns what, how the contract changes, what we assume about tenancy, and the steps for adding
a new part of the service.

## Decision 1: one service, several processes

- Marketing is one bounded service: this repo, one PostgreSQL database (`marketing`), one OpenAPI
  contract under `/v1/marketing`.
- Every process runs from the same image with its own entry point:
  - API: `uvicorn app.main:create_app --factory`
  - connector worker: `python -m app.workers.connector`
  - planned, same pattern: policy, media, webhook and event workers.
- No other service reads or writes these tables. Other systems use the API, or later the events
  this service publishes from its outbox.

below, and Dinesh reviews schema changes.

## Decision 3: contract versions

- The path carries the major version: `/v1/marketing`. Within v1, changes are additive only:
  new endpoints, new optional request fields and new response fields.
- Removing or renaming a field, changing its type or meaning, or making a request field required
  is a breaking change. It goes to `/v2/marketing`, and v1 stays until the frontend has moved.
- Enum values the UI switches on (for example `JobStage`) are published as enums. A new value is
  agreed with Praneeth before it ships.
- `contracts/openapi.json` is generated from the code (`uv run python -m scripts.export_openapi`).
  A test fails when it is stale, and CI compiles the generated TypeScript types.
- `contracts/examples/*.json` are the frontend's mocks. Tests check them against the schemas and
  check that every error example uses the status and `retryable` flag the API really sends.
- Outbox events carry `event_version` in the payload (`asset.generated` is version 1). A breaking
  payload change bumps it; consumers ignore fields they don't know.

## Decision 4: tenancy

- A tenant is one client account. Every business row belongs to exactly one tenant and has
  `tenant_id NOT NULL`.
- Tenant tables get `UNIQUE (tenant_id, id)`. A reference to another tenant table is composite,
  `(tenant_id, x_id) -> x (tenant_id, id)`, so the database refuses a link to another tenant's row
  even if the application has a bug.
- Row-level security is enabled and forced on every tenant table with the `tenant_isolation`
  policy on `app.tenant_id`. The setting is transaction-local (`set_config(..., true)`), set by
  `app.db.session.bind_tenant` in the API and for each leased event in the worker.
- Database roles: the owner runs migrations only. `marketing_app` (API) and `marketing_worker`
  (connector worker) don't own tables and don't have `BYPASSRLS`. Grants are explicit per table, and
  records that must never change (creative versions, validation runs, assets) get SELECT and
  INSERT only.
- The tenant comes from `X-Tenant-Id` and is checked against the user's active membership in the
  database on every request. Roles come from the database, not from Cognito groups.
- Allowed exceptions, each with its reason in `tests/test_isolation.py`:
  - `memberships` has no RLS, because `/me` lists a user's tenants before one is chosen.
  - `jobs -> creative_versions` doesn't carry `tenant_id`, because the same row is already tied to
    the tenant's creative.
  - `provider_spend` is a global counter with no tenant data.
  - The worker leases outbox rows across tenants only through the `lease_outbox_events()` function,
    which returns IDs only.
- Each process has a bounded pool (`DB_POOL_SIZE` + `DB_MAX_OVERFLOW`, default 5 + 5). Behaviour
  through RDS Proxy (pinning caused by `set_config` and asyncpg prepared statements) is not
  verified yet; that check runs on staging with the deployment work in NRC-26.

## Decision 5: shared conventions

| Topic | Rule |
|---|---|
| IDs | UUIDs generated by the application (`uuid4`). |
| Time | `timestamptz`, stored in UTC, ISO 8601 with offset in the API. Scheduled times also carry an IANA zone name (first used by NRC-14). |
| Language, currency | ISO 639-1 and ISO 4217 codes. |
| Money | Integer minor units in the API. Provider cost is kept internally in micro-USD. |
| Versioned records | Versions are immutable rows. The parent keeps `current_version`; edits send `If-Match`, and a stale version gets 412. |
| Commands | `Idempotency-Key` per tenant and route. The same key and body replay the first result; a different body gets 409. |
| Errors | `{code, message, request_id, details, retryable}`. Rejected input values are never echoed. |
| Lists | Cursor pagination with a capped `limit`. |
| States | Job execution state, policy outcome and publication state are separate fields. |

Each new table follows Decisions 4 and 5. The catalog tests in `tests/test_isolation.py` fail if
a new tenant table lacks forced RLS or a reference lacks `tenant_id`.

## Adding a module

1. Models in `app/models/<area>.py`, imported in `app/models/__init__.py`.
2. Migration: `uv run alembic revision --autogenerate -m "<what it adds>"`, then edit it by hand:
   RLS enable, force and policy; explicit grants per role; composite references; a `downgrade()`.
   Follow `docs/migrations.md`.
3. Schemas in `app/schemas`, logic in `app/services` (no FastAPI imports there), thin routes in
   `app/api/routes`, router added in `app/main.py` with `COMMON_ERROR_RESPONSES`.
4. A new kind of failure gets a class in `app/core/errors.py`; a new status category also gets an
   entry in `app/api/errors.py`.
5. Regenerate the contract, add examples for new responses and tell Praneeth.
6. Tests: another tenant's IDs give 404, role checks, idempotency and `If-Match` where they apply.
7. A new process uses the same image, its own entry point, its own database role if it needs
   different grants, and stops cleanly on SIGTERM.

## Consequences

- One database and one contract keep the three workstreams in step and let the database enforce
  tenant isolation.
- Adding a table costs a hand-edited migration and grants. The catalog tests make sure that work
  isn't skipped.
- Splitting a module into its own service later means moving its tables and exposing them through
  the API or events, which is possible because nothing outside reads them today.
